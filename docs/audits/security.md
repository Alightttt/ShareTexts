# ShareText — Security & Privacy Audit

Scope: frontend, Cloudflare Worker (Durable Object + Hibernation), Node signaling
server, WebRTC, WebSocket protocol, deployment config (Vercel / vercel.json), CSP,
CORS, logging, marketing copy. `npm audit`: **0 vulnerabilities**.

## Threat model

| Threat | Defense | Status |
|---|---|---|
| Random room discovery | roomId = crypto.randomUUID(); rooms never indexed/listed | ✅ |
| Code guessing / brute force | 6-digit TOTP (30s rotation, ±1 window) + per-room 10 fails/min (worker) + per-IP 10/min (Node) | ✅ |
| Third device joining | explicit 2-seat model → `ROOM_FULL` "already full" ack | ✅ |
| Room hijack / replay | TOTP window validation; resume requires the room secret (only ever handed to seated peers) | ✅ |
| Message injection / malformed frames | protocol version check; event allowlist; type checks; unknown events → `INVALID_MESSAGE` | ✅ |
| Oversized payloads | signal ≤64 KB; relay text ≤512 KB; relay binary ≤128 KB; socket.io `maxHttpBufferSize` 1 MB; Cloudflare frame cap | ✅ |
| Resource exhaustion | room idle-expiry (12 h) + empty expiry (4 h) + alarm-driven deletion; per-IP create limit 20/min | ✅ |
| XSS | messages render as plain text (`whitespace-pre-wrap`, never HTML); images via `<img>`/blob (no script execution in img context); video/audio native controls only; files are download-only, never inline-rendered | ✅ |
| Origin spoofing | strict origin allowlists on both servers; CORS reflects allowlisted origin only (never `*`); CSP `connect-src https:` for the worker, `frame-ancestors 'none'` | ✅ |
| CSRF | no cookies/auth; state changes require the random roomId; same-origin signals carry no ambient credentials | ✅ |
| Metadata leakage in logs | servers log only room-id prefixes, socket-id prefixes, IPs, lifecycle events — **never text, filenames, SDP, ICE, keys, or secrets** | ✅ |
| Content persistence | no message/file storage server-side; room storage deleted on close/expiry (DO `storage.deleteAll()`) | ✅ |
| Dependency vulnerabilities | `npm audit` clean | ✅ |
| Prototype pollution | inbound payloads are validated per-field before use; no dangerous `__proto__` merging | ✅ |

## Findings

### F1 — (MEDIUM, fixed) Relay privacy copy overstates the guarantee
- **WHAT** — RoomHub "How this works": *"your text is not readable by the relay."*
- **WHY** — The signaling server generates/possesses the room secret, so it *could*
  derive the key and decrypt; it simply chooses not to (no storage, no logging). The
  copy claims a technical impossibility ("not readable") instead of a policy ("not
  read/stored/logged"). Honest, defensible copy matters — this is a privacy product.
- **FIX** — *"Text is encrypted between devices. When a direct connection isn't
  possible, an encrypted relay forwards your data — the relay never stores or logs
  your content."* Same fix in the chat connection popover ("Encryption: Enabled" stays).
- **VERIFY** — grep the UI for "readable by the relay"; re-read the popover copy.

### F2 — (LOW, documented) Join links expose the internal roomId
- **WHAT** — `?join=<roomId>` in share links.
- **WHY** — It's a random 128-bit capability token: not guessable, room capped at two
  seats, and it never appears in logs. A short-code link would die with the 30s TOTP
  rotation. Acceptable; documented here and in the pairing audit.
- **FIX** — none required. Monitor for a link-leak complaint before adding a code-based
  link scheme.

### F3 — (LOW, documented) True E2E against the signaling provider is not claimed
- **WHAT** — The room secret is generated by the signaling server (Node) / the Worker
  (CF), so the key is derivable server-side. The app never claims "end-to-end
  encryption" — it claims "encrypted between devices," which is accurate.
- **WHY** — Real E2E against the signaling provider is impossible without trusting it
  anyway: it sees the WebRTC signaling in plaintext and could MITM the handshake. The
  honest position — encrypted, relay never stores/logs — is what the UI now says.
- **FIX** — none. If a future version wants peer-verified E2E, do a Signal-style
  key-verification step (compare 2×5 digits) over the already-established channel.

### F4 — (INFO) Session messages persist in localStorage
- **WHAT** — Last 100 messages (including text) are stored client-side for rejoin.
- **WHY** — Standard for a "rejoin anytime" promise; scoped to the device.
- **FIX** — none. Could add a "Clear history" affordance later.
